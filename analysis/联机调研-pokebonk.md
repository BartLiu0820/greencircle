# 联机调研：PokéBonk 合作模式

调研对象：https://pokebonk.com/ （v0.8.86，3D 宝可梦幸存者类，浏览器里 2~N 人合作）。
方法：读它公开的前端打包文件 `assets/main--*.js`（Vite + three.js），没有登录、没有建游客账号，所以房间里的实际流量没有抓包，下面都是从代码读出来的。

## 一、整体链路

```
浏览器 ──REST/长轮询──▶ api.pokebonk.com/coop/*   （大厅、房间状态、聊天、信令中转、TURN 凭证）
浏览器 ◀══WebRTC DataChannel 全网状直连══▶ 其他玩家   （对局内所有同步）
```

服务器只管"把人凑到一起 + 转发 SDP"，**对局时不过服务器**（除非走 TURN 中继）。

### 1. 大厅 / 房间（REST，`/coop/...?p=7`，p 是协议版本）

| 接口 | 作用 |
|---|---|
| `POST /rooms` | 建房（返回房间码） |
| `POST /rooms/{code}/join` | 用房间码加入，带上选的宝可梦 / 皮肤 |
| `POST /quick`、`GET /seeking` | 快速匹配、查有没有在找人的公开房 |
| `POST /rooms/{code}/open` | 房主开放空位（公开 / 好友可见） |
| `GET /rooms/{code}?after=&chat=&v=` | **长轮询拿房间状态**：带上已知版本号，没变就回 `same`；带聊天游标 |
| `POST .../chat` `/me` `/settings` `/vote` `/kick` | 聊天、改自己的准备 / 角色、房主改设置、投票、踢人 |
| `POST .../signal {to, kind, data}` | **WebRTC 信令中转**（offer / answer / bye），对方在下一次轮询里收到 |
| `POST .../start` `/again` | 开始、再来一局 |
| `POST .../leave`、`leave?soft=1` | 离开；页面隐藏时用 `keepalive` 发软离开 |
| `POST .../invite`、`GET /invites` | 好友邀请 |
| `GET /ice` | 取 STUN/TURN 服务器列表（含临时凭证），失败退回内置 STUN |
| `GET .../standing`、`/team`、`/coop/board` | 局后结算、队伍战绩、合作排行榜 |

细节：
- 轮询间隔大约 0.7 秒（刚发了信令时）到 5 秒（所有人都连上之后）；连续失败 6 次或 404/410/403 就退出房间。
- 进房时检查版本号，别人版本不同显示"对方版本不一样，请刷新"，不让开。
- 公开房有自动开始倒计时；有人没准备好或直连没全部打通时倒计时暂停（held）。房主挂机会超时。

### 2. 打洞 / 连接（WebRTC）

- **全网状**：每两人一条 `RTCPeerConnection`，slot 大的一方发 offer。
- 每条连接两个预协商好的 DataChannel：
  - `ctl`：可靠、有序、JSON。房间控制和对局事件都走它，自带 `_ping/_pong` 测 RTT。
  - `snap`：**不可靠、无序（maxRetransmits:0）、二进制 ArrayBuffer**，只发位置快照；缓冲超过 16KB 就直接丢这一帧。
- 连不上时按顺序换策略：`direct（只用 STUN）→ relay（只用 TURN）→ all`，每种重试几次。
  用过中继的设备在 localStorage 里记 7 天，下次先走中继；手机流量（`navigator.connection.type === 'cellular'`）也先走中继。
- 记录 ICE 候选统计（host / srflx / relay 各几个）和出错码，用于排查谁连不上。
- 每 1.5 秒互相广播"我和谁连通了"（`links`），全员互通才算 meshReady。

### 3. 对局同步：不是锁步，也不是单一主机，而是"谁刷的怪谁算"

这是最值得借鉴的地方：
- **每个客户端只模拟自己的角色和自己刷出来的怪**，别人的怪在本地是代理（`Remote` 标记），只插值显示。
- **快照按人裁剪**：给每个队友只发他视野中心 52 范围内、离他最近的怪；每帧条数在 30~170 之间自适应（连续发成功 45 次加 12 条，失败乘 0.7）；走中继的人隔一帧才发一次。
- **新怪先走可靠通道描述一次**（`en`：种类、标记、血量上限、伤害、体型、位置），之后快照里只带 key（下标 + 代数，防止复用下标认错怪）、坐标、血量百分比、状态位；收方不认识某个 key 就回 `want` 要描述。
- **打别人的怪**：本地攒成批，用 `hit` 发给怪的主人，主人那边结算伤害；怪死了主人广播 `dead`，经验掉落等跟着走。
- **主机**只是"当前在线里 slot 最小的人"，掉线自动换下一个；Boss 单独有一个 Boss 权威（bossAuthority）。
- 其他对局消息：`k` 击杀 / 伤害 / 等级统计，`xp` 分享经验，`down`/`rv`/`rvok` 倒地和救人，`pz` 暂停投票（合作时打开菜单不暂停，要全队投票），`ping` 轮盘标记，`sn` 小地图共享，`portal`/`go` 换关，`end` 结束，`bye` 离开。
- 难度按人数倍乘：刷怪数 `spawnMul[size]`、血量 `hpMul[size]`、Boss 血量另算。
- 选升级时角色被泡泡罩住（无敌但不能攻击），有时间预算并互相校验，防止靠卡选择界面无敌。

## 二、对我们（绿色循环圈 H5）的参考

现状：`game.js` 的玩家名单、多人规模（2~8 人、N 个出怪口、怪物上限 40×N）都已写好，留了 `window.GC_NET.send(事件)` / `window.GC.receive(事件)` 的口子，还没有联机层。

建议照搬的部分：
1. **服务器只做大厅 + 信令**：房间码、加入、准备、聊天、踢人 / 投票、开始，外加 `/signal` 中转和 `/ice` 下发 TURN 临时凭证。用 HTTP 长轮询就够，一个小服务（比如 Cloudflare Worker + Durable Object）能扛。
2. **WebRTC 全网状 + 两条通道**：可靠的 `ctl` 发事件（建塔、升级、卖塔、投票、点赞、复制 / 收购卷轴……也就是我们现在 GC_NET 那些事件），不可靠的 `snap` 发怪物位置。8 人是 28 条连接，DataChannel 可以接受。
3. **direct → relay → all 的回退梯子 + 记住需要中继的设备**，这对国内手机网络尤其重要，必须有自己的 TURN。
4. **"谁的出怪口谁算"**：我们每个玩家天然有自己的出怪口，正好对应 PokéBonk 的"谁刷的怪谁算"——每人模拟自己口出来的怪，别人只看代理；塔打到别人口的怪就发 `hit` 给主人结算。最终波 / 龙 / 魔王、整局计时、投票这类全局东西交给 slot 最小的在线玩家，掉线自动顺延。
5. 进房校验版本号、页面隐藏时 keepalive 软离开、掉线以后的重连窗口。

要另外想的：
- 原图（war3）是锁步同步。我们如果想严格还原随机效果（掉落、触发概率），也可以考虑锁步：只同步操作，各端用同一个种子的确定性随机数一起算。好处是流量极小、天然一致；坏处是一人卡全员卡，手机上体验差，而且 `game.js` 里所有 `Math.random` 和浮点误差都得收拾干净。PokéBonk 选的是"按归属分别权威"，更抗网络抖动，推荐我们也这么做。
- 塔防里塔会跨口打怪，比 PokéBonk 的打别人怪更频繁，`hit` 要批量合并、限频。
- 金钱 / 木材、复制 / 收购卷轴这些经济操作要由一个权威（建议当前主机）确认，避免双花。
